# 读按学到的依赖合成，一次往返取回

使用方的处理函数是一串串行的读：先查 session，再用它的 username 查 user、未读数、分组；先查一页提交，
再按每行的 problem_id 查题目（N+1）。lab 上按 HHHOJ 的真实接口测（bench/lab/README.md，“Real read shapes”）：
同样的读，改写成更少的语句后，1 线程、往返 500 µs 时快 4–10 倍，服务端打满（16 线程）时仍快 1.5–3.6 倍；
只把互不依赖的读 pipeline 起来，服务端打满时没有收益。要的是**更少的语句**，而且不能让使用方改写代码。

先行工作：Scalpel（Bowman & Salem，SIGMOD 2004）在 JDBC 层观察查询流，学到“外层结果是内层参数”的模式后改写成
join 预取；batched bindings（Guravannavar & Sudarshan，VLDB 2008）把循环里的参数化查询改写成一条集合查询；
Sloth（SIGMOD 2014）用延迟求值攒批。前者要理解 SQL 才能改写，后两者要静态分析或代理类型。

决定：

- **观察。** 一个作用域是一个 `pg::conn` 上、两次写之间的读（`conn::query` / `query_one` / `query_opt`，
  语句以 SELECT 开头、不锁行、不 pin）。写、`send`、事务、`raw()` 都结束作用域。作用域的第一条读是**根**。
  每条读记下模板（渲染后的文本）、参数和结果。
- **来源。** 作用域结束时，对每条后来的读的每个参数找来源：根的第 i 个参数；根或另一条读的结果第 c 列
  （列类型等于服务端为这个参数推断的类型，字节相等）；字面值。一条读的参数都有来源，它才是**跟随读**；
  按父读的每一行各执行一次的是**逐行**跟随读。转换过的值（拼成数组字面量等）没有来源，不预取。
- **学习。** 池按根的模板记每条跟随读的签名（模板、各参数来源、父读）出现的比例，按 0.97 指数衰减。
  根出现至少 8 次、比例至少 0.95 时进入计划；掉下去就移出。字面值是签名的一部分，只有每次相同的值才会达到比例。
  从没有过跟随读的根，64 个作用域之后只按 1/64 抽样观察。
- **合成。** 根执行时如果有计划，计划里的语句放进**一个**批次，和根一次往返，在专用的只读会话上执行：
  这类会话用启动选项 `default_transaction_read_only=on` 和 `statement_timeout=250` 打开（最多
  `max(1, max_conns / 4)` 个，不占 `max_conns`，从不借出），pipeline 的每个隐式事务因此都是只读的，服务端拒绝其中
  的任何写（包括函数里的写和 `nextval`）。发送前和批次落地后都用 ParameterStatus 核对会话仍报告
  `default_transaction_read_only=on`；被函数改成 off 的会话直接丢弃。`pooler` 模式不发启动选项，
  只读会话无从建立，所以预取关闭。
  - 父读（根，或只依赖根参数、字面值的跟随读）连同它的逐行跟随读合成一条：
    `SELECT k.*, f0.* … FROM (SELECT row_number() OVER () AS n, t.* FROM (父读) t(c1…)) k
     LEFT JOIN LATERAL (SELECT row_number() OVER () AS r, x.* FROM (F0[$j:=k.cX]) x) f0 ON true … ORDER BY k.n`。
    父读的结果按 n 的顺序从这条语句里切出来，不再单独执行；每个跟随读的行按 r 切出。每条至多一个每键多行的成员。
  - 其余每键多行的跟随读用 `SELECT DISTINCT 键 … LIMIT 1001` 取键，各一条。
  LATERAL 让任意参数化查询对每个键各执行一次，ORDER BY、LIMIT、聚合的语义和逐次调用相同，不需要理解 F 的 SQL。
  计划的语句只渲染一次，之后每个作用域只填参数。
- **使用。** 切出来的结果按（模板，参数字节）排队放进作用域缓存，一个结果只回答一次读。命中不往返；
  没命中照常执行，并清掉整个缓存（没预测到的读可能是写）。连接上还有没读完的 `send` 时不合成、不命中。
- **不预取：** 事务里；锁定读；pin 语句；学到的根平均耗时超过 50 ms 或平均超过 1000 行。
  批次里的语句出错，只作废出错语句的成员，错误不给程序；根在批次里时改为正常执行一次。
- `pool_options::prefetch`，默认关（理由见 Consequences）。

## 不变式

1. 程序拿到的每个读结果，都等于那条语句在根发出之后、程序发出它之前某一时刻执行的结果，其间本连接没有写；
   每个结果只回答一次读。
2. 预取的部分不把错误抛给程序，不丢弃共用的线路连接，不写库。
3. 事务里不做预测性改写。
4. 浪费有上限并且可见：`pool_stats::prefetch_{plans,hits,misses,unused,failures,skips}`。

## Consequences

lab（bench/lab/README.md，“Learned prefetch”）上，代码不改、只打开 `prefetch`（pool 8，另有至多 2 个只读会话）：

| 接口 | 1 线程，往返 500 µs | 16 线程 | 手写最优（1 线程 / 16 线程） |
|---|---|---|---|
| auth/me（8 条读，1 条参数不可预测） | 163 → 425 | 703 → 958 | 713 / 1211 |
| 提交列表（N+1） | 126 → 1210 | 1285 → 4760 | 1252 / 5763 |
| 评测机轮询 | 256 → 1364 | 3154 → 8189 | 1076 / 6455 |
| 60/30/10 混合 | 149 → 556 | 868 → 1350 | 823 / 1480 |

- 往返主导时接近或超过手写最优；服务端打满时列表到手写最优的八成多，混合到九成，轮询超过手写最优。
  合成语句里的 LATERAL 和切结果是剩下的差距。
- 批次最初包在 BEGIN READ ONLY、250 ms 语句超时、ROLLBACK 三条保护语句里；只去掉它们，16 线程快 10–15%，
  换成只读会话快 9–50%（预测批次也不再和程序自己的语句挤在同一条线路连接上）。
- 客户端指令（callgrind，每个处理函数）：有计划的处理函数比串行**少**，因为发给 libpq 的语句少了——
  列表 167k → 134k，auth/me 102k → 95k，轮询 62k → 47k；没有可学模式的点查每条读多 4.7%。
  做到这一点靠三件事：只在计划里的跟随读被淘汰时才重建计划（参数是每次不同字面值的读每个作用域都会进出一次，
  原来每次都整份重建，me 的客户端指令因此从 123k 涨到 191k）；跟随读的结果是批次结果上的窗口，不再复制成新的 PGresult；
  作用域缓存按 64 位哈希查找、命中后核对文本和参数，不再为每次读拼字符串键。
  lab 的服务端独占一颗核，这些在 16 线程吞吐上只体现为 +2–8%；客户端和数据库共用 CPU 时省下的才是服务端的。
- 默认仍关：要多开只读连接；`pooler` 模式无效；下面的副作用限制；作用域里的预取结果没有存活时间上限，
  同一个 conn 先读、等待外部事件、再读时，后一次读拿到的是批次执行那一刻的数据（不变式 1 允许，但和串行执行
  的感受不同）。
- 每个根的前 8 个作用域照常执行，学到计划之后才合成。只读错误（25006）和语法、语义错误（42 类）永久作废跟随读，
  其他错误暂停 32 个作用域。
- 只读批次挡不住不受事务控制的副作用：被预取的函数里拿会话级 advisory 锁、`dblink_exec` 之类，即使程序没有发出
  这条读也会生效。函数在会话级把 `default_transaction_read_only` 改成 off 也属此类：会话在那个批次落地后丢弃，
  但已经排在它后面、同一会话上的批次按读写执行。调用这类函数的读不要打开 `prefetch`。
