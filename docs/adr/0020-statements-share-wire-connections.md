# 事务外的语句共用线路连接，连接只在需要时独占

数据库在远端时（同区 RTT 0.5–1 ms），一条语句从发出到结果回来的整个往返里，服务端大部分时间是空闲的。
如果连接在往返期间被独占，max_conns 条连接最多只能跑 max_conns / RTT 条语句每秒；而使用方（HHHOJ）
的常态是线程数多于连接数（固定 8 条连接），多出来的线程只能排队借连接。

决定：

- 事务外的语句只在发送的那一刻占用线路连接，发完就把连接还给池，再按发送顺序收自己的结果
  （每个往返对应一个 ticket，由正在等待的线程之一负责读取并分发）。下一条语句可以接着发在同一条线路连接上，
  也就是跨线程的 pipeline。
- 事务、`raw()`、`session_of()`，以及开头不是 SELECT/INSERT/UPDATE/DELETE/WITH/VALUES/TABLE、
  或者提到 advisory、set_config、currval、lastval、pg_backend_pid 的语句，会让连接独占一条线路连接
  直到它结束，行为和以前一样。
- COMMIT 发出后就把连接还给池，下一个事务的语句可以紧跟在 COMMIT 后面发出。
- 构造 `pg::conn` 时，池里有空闲的线路连接就不独占；池已满且没有空闲时，照旧等待，
  所以 acquire_timeout、熔断以及 max_conns 对服务端连接数的上限都不变。
- 选择线路连接时，挑在途往返最少的那条；最少的那条也有在途往返且池没满时，先开新连接。
  已知很慢的语句（按语句文本学习的耗时超过 2 倍往返时间，且至少 1 ms），或者队头卡住超过这个时间的
  线路连接，不往它后面排。

## Consequences

在 RTT 约 0.8 ms、8 条连接、64 个线程时：单行查询从 10.9k 提到 84k ops/s（p50 从 6 ms 降到 0.75 ms，
约等于一个往返）；50 行的列表页从 11.3k 提到 39.6k（受测试代理限制）；tx3 事务从 2.7k 提到 3.7k。
本机直连时同样提升，单行查询从 132k 提到 161k。

- 语句在 pipeline 里会排在同一条线路连接上先发出的语句后面。第一次执行的慢语句，在被识别出来之前，
  可能让后面排上来的语句多等它一次；之后同文本的语句会被绕开。
- `pool_stats::leased` 只统计独占中的连接，不再等于存活的 `pg::conn` 个数。
- 一条线路连接断开或超过截止时间时，在它上面排队的所有语句一起失败。
