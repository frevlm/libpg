# 语句可以先发出、后取结果

使用方的处理函数里，每次阻塞调用都要等一个往返，有两种常见的浪费：

- 列表页先发 `SELECT count(*)`，再发列表查询。两条读互不依赖，却花了两个往返。
- 事务先 `SELECT ... FOR UPDATE`，接着发几条 INSERT/DELETE（返回值都被丢弃），再 COMMIT。
  只有 SELECT 的结果需要等，可连接和行锁却被占用了 1 + N 个往返。

决定：

- `conn::send<T...>(sql)` 把语句排进 pipeline 立即返回 `pending<T...>`；`all()`、`one()`、`opt()`、`affected()`
  读取结果，每个 `pending` 只能读一次。结果列的类型检查在语句执行前完成，和 `query` 一样。
- 有未读语句的 `conn` 独占一条线路连接，语句在它上面按发送顺序执行；事务里和事务外都一样。
- 事务里没人读的语句由 `commit()` 检查：先读完所有未读语句，有失败就回滚并抛出它的错误（先发语句的根因，
  而不是 "current transaction is aborted"）。
- `conn` 结束时先读完它发出的每条语句，所以 `pending` 在 `conn` 结束后仍然能读。事务外没人读的语句如果出错，错误被丢弃。

## Consequences

- 事务里先发的写语句失败时，错误由下一条读取它的语句或 `commit()` 抛出。
- 不需要结果的写入写成 `(void)c.send(...)`；事务外这样写不保证它已经执行成功。
