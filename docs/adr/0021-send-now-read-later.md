# 语句可以先发出、后取结果

使用方的处理函数里，每次阻塞调用都要等一个往返，有两种常见的浪费：

- 列表页先发 `SELECT count(*)`，再发列表查询。两条读互不依赖，却花了两个往返。
- 事务先 `SELECT ... FOR UPDATE`，接着发几条 INSERT/DELETE（返回值都被丢弃），再 COMMIT。
  只有 SELECT 的结果需要等，可连接和行锁却被占用了 1 + N 个往返。

决定：

- `conn::send<T...>(sql)` 发出语句立即返回 `pending<T...>`；`all()`、`one()`、`opt()`、`affected()`
  等结果并读取，每个结果只能读一次。
- 事务外先发的语句各自浮动，彼此之间以及和这个连接后续的语句之间都没有顺序。
- 事务里先发的语句按顺序走事务自己的线路连接。没人读的语句由 commit 检查：COMMIT 先发出，再等这些语句，
  有失败就抛出它的错误。此时服务端已经把这次 COMMIT 当作 ROLLBACK 执行。后续语句失败时，
  抛出的是先发语句的错误（根因），而不是 "current transaction is aborted"。
- 连接结束前会等完它发出的每条语句。事务外没人读的语句如果出错，错误会丢失。

## Consequences

部署机上实测（docker 网络，RTT 约 70 µs，2 vCPU）：列表页的两条读改成先发后取后，单线程从 5.3k 提到 7.2k 页每秒。
热点行事务基本不变，因为每笔约 1 ms 的耗时主要是 COMMIT 等 WAL 落盘，不是往返。

- 错误抛出的位置变了：事务里先发的写语句失败时，由下一条语句或 commit 抛出。
- 事务外先发的写语句，不能假定它对同一个连接后面的语句可见。
