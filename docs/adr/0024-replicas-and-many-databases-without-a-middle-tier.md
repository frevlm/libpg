# 多副本、多数据库：库内分片，连接收拢交给事务池化器，不自建中间层

使用方要上 k8s：同一个服务跑多个副本（pod），数据分布在多台数据库服务器上；本地和单机部署照常可用。
要解决的是大并发下的两件事：

- 数据怎么分到多个库；
- 副本数增长时，服务端连接数怎么不随之爆掉。

候选之一是自建中间服务 pgd：应用只连 pgd，pgd 连 PG，每个缓存 key 归一个 pgd 实例管。

## 测得的事实

- 进程内缓存格子读加累加约 0.8 µs；一次网络往返 70 µs（docker），k8s 跨节点 100–300 µs。
- 计数器增量满足交换律，`UPDATE … SET c = c + $1` 本身就把各副本的写入串行化了：PG 已经是每个格子唯一的归属方。
- 直连时服务端连接数 = 副本数 × max_conns。实验平台（`max_connections=100`，每个 pod 8 条连接，24 个 pod 同时起）：
  24 个 pod 里有 14 个连不上；10 个 pod 时 p999 已经到 1.3 s。
- 同样 24 个 pod 经过 PgBouncer（transaction 模式，16 条服务端连接）：全部跑起来，单行查询 p999 为 83 ms。
  在这台 2 核机器上，PgBouncer 和 PG 抢同一个核，总吞吐是直连的 55–65%。
  这个吞吐比例反映的是实验机的 CPU，不代表生产环境。
- 在 PgBouncer 1.26 的 transaction 模式下，以下功能全部可用：pipeline、跨线程共用线路连接、预编译语句
  （`max_prepared_statements`）、先发后取、事务、格子、binary COPY。
  不可用的有三类，都属于会话级的东西：
  - 启动参数里的设置（连接直接被拒）；
  - `LISTEN`；
  - 依赖 backend pid 的判断。

## 决定

不建 pgd。在现有语义下（缓存写在内存确认、读可以短暂过时），pgd 删不掉 writeback 的主要部件：

- 回执（0012）仍然需要：pgd 写 PG 时，COMMIT 中途断连照样可能发生；
- 每笔一个保存点的重做仍然需要；
- NOTIFY 对齐（0013）仍然需要：管理后台、手工 SQL 会绕过 pgd 直接写库；
- 缓存读写如果走 pgd，每次多一个往返。

pgd 唯一独有的收益是收拢连接，而这件事 PgBouncer 和 PgCat 已经做好了。

- **分片**：`pg::sharded<T>` 每个分片持有一个 T，`of(key...)` 用 jump consistent hash 选分片。
  - key 的哈希与进程、编译、平台无关：整数统一扩成 64 位，文本带长度前缀。
  - 新分片只能加在末尾，加一个分片只会迁走 1/(n+1) 的 key。
  - 一笔业务（事务、一笔写回）必须落在同一个分片上，不做跨分片事务。
- **连接收拢**：池选项 `pooler = true` 表示 DSN 指向事务池化器。
  - 此时不发送启动参数，`statement_timeout` 和 `synchronous_commit` 改在角色上设置（`ALTER ROLE … SET`）。
  - writeback 的写入线程和监听线程需要会话级能力，通过 `writeback_options::direct_dsn` 直连服务器。
    每个副本、每个分片各 2 条直连。
- **对 k8s 的接口**：
  - `pool::ready()` 用于就绪检查：有连接且熔断未打开时为真；没有连接时试连一次；不会在繁忙的池上排队。
  - SIGTERM 时析构 writeback，在 `shutdown_timeout` 内刷完积压（0014）。
    `terminationGracePeriodSeconds` 必须大于这个时长。
  - 配置由使用方读取后传进来，调度、扩缩容、服务发现都交给 k8s。
- **本地模式**：同一份代码，只配一个分片，不配池化器。

## Considered Options

- **自建 pgd 中间层**：缺点见“决定”。出现以下情况时重新评估：
  - 需要在线迁移分片，又不能重新部署应用；
  - 直连 writeback 的连接数（副本数 × 分片数 × 2）本身逼近上限。
- **只靠库内路由、不用池化器**：副本数 × max_conns 超过 `max_connections` 后，新副本直接连不上（实测 24 个 pod 里有 14 个失败）。

## Consequences

- 部署时按公式核算服务端连接数：
  - 经过池化器：池化器的服务端连接数 + 副本数 × 分片数 × 2（writeback 直连）；
  - 直连：副本数 × 分片数 × max_conns。
- 经过池化器时，SET 和 advisory lock 这类会话状态只在一个事务内有效。
- 经过池化器时，迁移改变了某条语句的结果类型（例如 `SELECT *` 的表加了列）后，池化器缓存的预编译语句会报 0A000，
  直到它的服务端连接被回收。迁移后应在 PgBouncer 上执行 `RECONNECT`。
- 同一个缓存格子在各副本内存里的值，会在一个写回周期内不一致（0013 不变）。
