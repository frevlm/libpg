# 写回缓存的内存值靠定期重读保持新鲜，不用 LISTEN/NOTIFY

槽里的值是“最近一次读到的数据库值加上本进程已记账未结算的增量”。写回线程每个 `interval` 先做一轮刷新，再写批次：

- 最近 `refresh`（默认 1 秒）内没被读过、也没有未结算增量的槽被丢掉，内存不随历史键增长。
- 已加载、自上次加载起被读过、且加载时间超过 `refresh` 的槽被重读：每个计数器一条语句，键以类型化数组传入
  （`unnest(...) WITH ORDINALITY` 联表），把槽的数据库值换成读到的值；未结算的增量原样保留，所以对别的副本、
  管理后台、手工 SQL 的写入，内存值最多落后 `refresh` 加一个 `interval`。
- 读写用一把读写锁隔开：加载（共享）不会在“批次已提交、尚未结算”的瞬间读到数据库值，否则同一个增量会被算两次；
  写线程的刷新和批次占用独占一侧。刷新出错不影响同一轮的批次，下一轮再试。
- `get` 对内存里没有的键只做一次 SELECT 加载，行不存在抛 `not_found`。

理由：这个值是准入判断用的估计，不是账本；账本是数据库，写回批次对它做原子加法，不依赖内存值是否最新。
滞后的上界是配置项，而且不需要任何数据库端对象：没有触发器、没有每个写入事务里的 NOTIFY（它在提交时争一把全库锁，
把提交串行化），没有专用的 LISTEN 连接和它的重连与全量对齐逻辑，也没有“绝对值写入覆盖别的副本增量”这类要使用方记住的规则。
读取的代价由 `refresh` 控制：热键每秒一条语句（按计数器合并），冷键不占内存。

## Considered Options

- 触发器加 NOTIFY：滞后更小，但每个写入者的事务都付出提交锁的代价，库里要建触发器，还要处理监听连接断线。
- 不刷新，只在重启后对齐：多副本时内存值随别的副本的消费无限偏离。

## Consequences

- 对计数器的绝对值写入（`UPDATE ... SET c = 100`）仍会覆盖别的副本还没写回的增量；计数器列只应通过增量修改。
- `refresh` 越小越新鲜，热键的重读越频繁；调大则相反。需要立刻生效的低频写入直接在事务里执行 SQL，
  各副本在下一次刷新时看到。
